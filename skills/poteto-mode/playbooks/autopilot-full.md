### Autopilot-full

**You own the verdicts, never the PRs. One owner role runs each PR from build to merge, and nothing merges without an independent clean verdict.** Use only when the operator explicitly asks for full autopilot and grants publication and merge authority for the named queue.

1. **Load the runtime and record authority.** Resolve delegation, waiting, scheduling, control, and current-task history through **bstack-runtime**. Record the durable objective, exact queue, and grants for commit, push, PR creation, branch rewriting, and merge. Operator-owned items stop at merge-ready. A request to explain the protocol is not permission to execute it. Honor existing grants without asking again. Operator gates and host or forge security approvals remain required.
2. **Give one owner each independent PR.** Each owner gets a disjoint branch or worktree, explicit write scope, acceptance checks, PR conventions, a live verification recipe, and the **poteto-worker** contract. Use the fresh-worker lifecycle in [Poteto mode](../SKILL.md#subagents), including full original and later directives and the prior report and branch. Run owners within configured runtime and host limits. Serialize overlapping work. If delegation is unavailable or forbidden, perform permitted work locally and record any missing independent verification.

   Start a local `decisions.tsv` trail through **show-me-your-work** at the beginning of the assignment. Save evidence after each verifiable unit. Commit and push each unit to the owner's branch only when those actions are authorized, with hooks enabled. Open an early PR only with publication authority, following [Opening a PR](opening-a-pr.md) and user draft preferences. Without that authority, retain local artifacts and report the blocked action. Keep trails local unless their publication is authorized. On each child launch, record its ID, route, expected runtime and its basis, state, owned scope, and last durable evidence in `children.tsv`. Use prior comparable runs to inform expected runtime.
3. **Report code-ready before waiting for merge-ready.** The owner builds, tests, triages findings, runs available cleanup and **no-comments**, and rebases its own branch onto current trunk before the first code-ready report and babysit. During fix rounds, keep that base unless merge prep, a demonstrated conflict with trunk, or a trunk-caused CI failure requires another rebase. Each history rewrite needs authority. Publish a rewrite only with explicit force-push authority, a fresh remote-SHA check, and a lease pinned to that SHA. Never rewrite a shared branch.

   Run the required pre-review checks for touched paths on the exact reported head. Hooks alone are not proof. Report the code-ready SHA and each later SHA whose patch changes. Self-proof, CI, and the assigned babysit loop may then run alongside independent verification within runtime limits. Report merge-ready only after all required receipts and checks exist at the current head.
4. **Verify each round independently.** Start a round at code-ready and every changed-patch round, including fix rounds. Use **swarm** at the exact reported SHA. Include repository gates, live checks for the load-bearing behavior on every affected surface, performance checks when relevant, and at least two focused audit lanes. Give each audit lane the full consolidated brief and a distinct focus, such as consumer parity, lifetimes and races, or data and configuration safety. Run the load-bearing scenario on current trunk too. If trunk lacks the feature, record that fact and verify the added behavior and user-visible end state. Missing required evidence or independent review prevents a clean verdict.

   Inspect the merge-ready receipts before finalizing the verdict. Send every proven issue against the PR, including defects labeled as notes, in one fix-forward brief to a fresh owner. For each behavior defect, require a failing test and passing fix covering every affected site under the local test-contract guidance. Use reproducible receipts when a test cannot demonstrate the defect. Carry those defects into the next review brief. Respect configured review-round limits and report unresolved work at the limit. Reuse a verdict or lane only under [Shipping's verification reuse rule](shipping.md#verification-reuse).
5. **Merge only at the authorization intersection.** Begin merge prep after the round's lanes start. Rebase onto current trunk for merge prep when authorized, report the new SHA, and wait for CI on that head. Apply [Shipping's verification reuse rule](shipping.md#verification-reuse) after every change. Immediately before merge, fetch current trunk and confirm a clean merge with `git merge-tree` or an equivalent repository check. Compare trunk changes since the head's merge base against the PR's changed paths and paths controlling its CI. A conflict or overlap requires another rebase, current-head CI, and a freshness check. A disjoint trunk advance alone need not restart that cycle.

   Confirm the forge's current head, mergeability, required checks, and operator gates. Merge only that exact PR and head within the operator's scoped grant and the root's clean verdict. Neither autonomy nor a verdict supplies absent authority. Never infer deploy authority. Operator-owned items wait for the operator. After completion, a fresh owner takes the next queue item.
6. **Audit hourly through the runtime.** For an authorized running program, use the runtime's schedule or wake capability for an hourly audit. If unavailable, use bounded in-turn waits, checkpoint durably, and report that continuous monitoring is unavailable. Re-read this playbook from the current installed bstack root and the recorded objective at every audit. Probe owners, the runtime's agent list when available, and every `children.tsv`. Inspect branch evidence and decision trails rather than accepting self-reported progress.

   Errors, inability to start a turn, or absent durable progress can justify stuck replacement after inspecting the process and artifacts. Expected runtime is diagnostic evidence, never an arbitrary kill deadline for an LLM call. Follow the runtime's same-route recovery policy without resetting its attempt budget. Record stuck children and preserve their work. Stop the prior writer before replacing it in the same scope; if cancellation cannot be confirmed, isolate the replacement and prevent shared writes. The root handles recovery when the owner cannot. A stall never drops a required lane. Keep auditing until all delegated work ends, even after the last merge.

   Log each audit and notify the current task only of unreported changes, such as a new verdict, blocker, or replacement, under host and operator notification policy. Do not repeat unchanged tables or blockers unless periodic status was requested. A new pinned gate or budget increase still needs the designated approval and verifier evidence. A root countersign substitutes for operator approval only when the exact grant and approval contract allow it; it never bypasses host or forge security approvals.
7. **Honor stop immediately.** A hold or stand-down sends every owner and child a zero-writes instruction and cancels future scheduled work. Preserve their briefs and artifacts until released.

**Reply:** the queue with each PR's owner, state, and head SHA, each verdict, what merged, open operator gates, trail locations, and blockers.
