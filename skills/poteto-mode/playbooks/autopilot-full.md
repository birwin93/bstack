### Autopilot-full

**You own the verdicts, never the PRs. One owner role carries each PR from build to merge, and nothing merges until an independent swarm that never wrote the code has proven the code that lands.** Use only when the operator explicitly asks for full autopilot and grants publication and merge authority for the named queue.

A verdict covers one patch and green CI covers one head. Step 4 runs a full swarm once, and again only for a major change. [Shipping's verification reuse rule](shipping.md#verification-reuse) can carry a lane's result to a new head. Every new head still needs its own green CI.

1. **Load the runtime and record authority.** Resolve delegation, waiting, scheduling, control, and current-task history through **bstack-runtime**. Record the durable objective, exact queue, and grants for commit, push, PR creation, branch rewriting, and merge. Operator-owned items and PRs outside the queue stop at merge-ready. A request to explain the protocol is not permission to execute it. Honor existing grants without asking again. Operator gates and host or forge security approvals remain required.
2. **Give one owner each independent PR.** Each owner gets a disjoint branch or worktree off trunk, explicit write scope, acceptance checks, PR conventions, a live verification recipe, and the **poteto-worker** contract. Never stack owners, so each PR lands on its own. Use the fresh-worker lifecycle in [Poteto mode](../SKILL.md#subagents), including full original and later directives and the prior report and branch. Run owners within configured runtime and host limits. Serialize overlapping work. If delegation is unavailable or forbidden, perform permitted work locally and record any missing independent verification.

   Assume an owner can die at any point, and keep its work where a replacement can find it. Start a local `decisions.tsv` trail through **show-me-your-work** at the beginning of the assignment. Save evidence after each verifiable unit. Commit and push each unit to the owner's branch only when those actions are authorized, with hooks enabled. Open an early PR only with publication authority, following [Opening a PR](opening-a-pr.md) and user draft preferences, so CI and bots run alongside the work. Without that authority, retain local artifacts and report the blocked action. Keep trails local unless their publication is authorized. Whoever launches a child records its ID, route, expected runtime and its basis, state, owned scope, and last durable evidence in `children.tsv`, so the root can probe it if the parent dies. Use prior comparable runs to inform expected runtime.
3. **Report code-ready before waiting for merge-ready.** The owner builds, tests, triages findings, runs available cleanup and **no-comments**, and only then calls the code ready, so the full swarm runs on finished code. It rebases its own branch onto current trunk before the first code-ready report and babysit, so verification runs on the base the patch lands on. During fix rounds, keep that base unless merge prep, a demonstrated conflict with trunk, or a trunk-caused CI failure requires another rebase, because each rebase restarts CI. Each history rewrite needs authority. Publish a rewrite only with explicit force-push authority, a fresh remote-SHA check, and a lease pinned to the SHA the owner last pushed or took over. Never rewrite a shared branch. On any push the owner did not make, it stops and reports to the root.

   Run the required pre-review checks for touched paths on the exact reported head, before the code-ready push and before any later push that needs a verifier. Hooks alone are not proof. Report the code-ready SHA and every later SHA. Self-proof, CI, and the assigned babysit loop may then run alongside independent verification within runtime limits. Report merge-ready only after all required receipts and checks exist at the current head.
4. **Run one full swarm, then verify each later head.** A full swarm runs once, at the code-ready head. Another full swarm runs only for new behavior, a redesign, or a large new diff. A rebase, a merge-conflict resolution, or a minor fix gets a single fresh verifier at the new head. Run each full swarm through **swarm** at the exact reported SHA. Include repository gates, live checks for the load-bearing behavior on every affected surface, performance checks when relevant, and at least two focused audit lanes. Give each audit lane the full consolidated brief and a distinct focus, such as consumer parity, lifetimes and races, or data and configuration safety. Run the load-bearing scenario on current trunk too. If trunk lacks the feature, record that fact and verify the added behavior and user-visible end state. Missing required evidence or independent review prevents a clean verdict.

   Inspect the merge-ready receipts before finalizing the verdict, because no lane trusts a claim it has not checked. Send every proven issue against the PR, including defects labeled as notes, in one fix-forward brief to a fresh owner. A defect trunk shows without the PR is recorded against trunk and does not gate the PR. A defect the PR copies or newly reaches is the PR's own. For each behavior defect, require a failing test and passing fix covering every affected site under the local test-contract guidance. Use reproducible receipts when a test cannot demonstrate the defect. Carry those defects into the next review brief. The root never pushes a fix itself, because each branch has one writer. It replaces a stuck owner instead. Respect configured review-round limits and report unresolved work at the limit. Reuse a verdict or lane only under [Shipping's verification reuse rule](shipping.md#verification-reuse).
5. **Merge only what was verified, tested on the trunk it lands on.** Green CI alone never authorizes a merge. Begin merge prep after the round's lanes start. Rebase onto current trunk for merge prep when authorized, report the new SHA, and wait for CI on that head. Apply [Shipping's verification reuse rule](shipping.md#verification-reuse) after every change.

   Immediately before merge, fetch current trunk and ask whether its changes can affect the patch, because rebasing for every trunk move never ends. Check the merge with `git merge-tree` or an equivalent repository check. Compare trunk changes since the head's merge base against the PR's changed paths and the paths controlling its CI. Rebase and wait for CI when the code that would land was never tested together. That covers a conflict, a file both sides changed, or a change to which checks run for the PR. A lockfile both sides changed needs no rebase when a frozen install passes on the merge result and the packages the PR changes resolve there as on the head. That install tests the lockfile that would land, and a failing install means the rebase must repair it. When trunk changed a caller of the patch or something the patch depends on, such as code it calls or a dependency version, run the patch's checks on the merge result and merge on a pass. Otherwise merge. If trunk would force a third rebase past merge prep, hold and report to the root, which sequences the colliding work.

   Confirm the forge's current head, mergeability, required checks, and operator gates. Merge only that exact PR and head within the operator's scoped grant and the root's clean verdict. Neither autonomy nor a verdict supplies absent authority. Never infer deploy authority. Operator-owned items wait for the operator. After completion, a fresh owner takes the next queue item.
6. **Run the root layer and audit hourly through the runtime.** Anything that loosens a gate, such as a raised budget or an allowlist entry, needs a verifier's proof and then the root's fresh countersign, because the owner is the one who wants green. It also still needs the designated approval. A root countersign substitutes for operator approval only when the exact grant and approval contract allow it. Then the owner's record of the approval points at the countersign for a lane to check. A countersign never gives or bypasses a host or forge security approval. A disabled or soft-failed check always comes out, because it stops guarding every case.

   For an authorized running program, use the runtime's schedule or wake capability for an hourly audit until no delegated work is left, because long runs drift and agents stall silently. If unavailable, use bounded in-turn waits, checkpoint durably, and report that continuous monitoring is unavailable. Re-read this playbook from the current installed bstack root and the recorded objective at every audit. Fix drift, such as an unreported head or an unrecorded agent, by having its owner record it. Drift is a gap in the record, not a stall.

   Probe every agent, down to the leaf lanes, through owners, the runtime's agent list when available, and every `children.tsv`. Judge each by its side effects, such as commits, pushes, PR or check changes, and trail rows. Status text and summaries can hide a stuck child. An agent waiting on the root or the operator is not stuck. Answer it, or carry its question to the operator. Errors, inability to start a turn, or absent durable progress can justify stuck replacement after inspecting the process and artifacts. So can an owner with no trail row and no saved unit by the first audit. Expected runtime is diagnostic evidence, never an arbitrary kill deadline for an LLM call. Follow the runtime's same-route recovery policy without resetting its attempt budget. Record stuck children and preserve their work. Stop the prior writer before replacing it in the same scope; if cancellation cannot be confirmed, isolate the replacement and prevent shared writes. The root handles recovery when the owner cannot. A stall never drops a required lane. Keep auditing until all delegated work ends, even after the last merge.

   Log each audit. An audit that changed something for the operator, such as a new verdict, blocker, or replacement, ends by catching them up per **ketchup**, under host and operator notification policy. An audit that changed nothing stays quiet unless periodic status was requested.
7. **Honor stop immediately.** A hold or stand-down sends every owner and child a zero-writes instruction and cancels future scheduled work. Each owner reports where it stands. Preserve their briefs and artifacts until released.

**Reply:** catch the operator up per **ketchup**. Cover each PR's state and verdict, what merged, countersigns and why, open operator gates, and blockers, with links to each PR and the trail locations.
